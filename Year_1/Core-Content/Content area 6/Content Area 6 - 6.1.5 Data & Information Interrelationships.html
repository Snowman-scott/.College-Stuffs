Data, Information & Knowledge

💡

Knowledge

Understanding gained from experience, enabling informed decisions and actions

Example: "We should increase server capacity on Fridays because sales peak then"

📊

Information

Data processed and given context, revealing patterns and meaning

Example: "Website traffic increased 40% last Friday evening"

🔢

Data

Raw, unprocessed facts and figures without context or meaning

Example: "15.2, 23.8, 45.1, 18.7" (numbers without labels)

The Data-Information-Knowledge Hierarchy

📊 Data → Information → Knowledge

Each level builds upon the previous, adding context, analysis, and understanding.

Real-World Example: E-commerce Website

Timestamp: 14:35:22

Action: Click

→

Key Distinction

• Data answers "what?" • Information answers "what does it mean?" • Knowledge answers "what should we do?"

Data Generation Methods

🔄 How Data is Created Affects Its Value

The method used to generate data directly impacts its accuracy, reliability, completeness, and suitability for different purposes.

👥

Human-Generated

Methods: Surveys, forms, interviews, manual entry

Strengths: Captures opinions, qualitative insights, context

Weaknesses: Prone to bias, errors, slow, inconsistent

📡

Sensor/IoT

Methods: Automated measurement, continuous monitoring

Strengths: Objective, accurate, real-time, continuous

Weaknesses: No context, no "why", hardware failures

🤖

AI/ML

Methods: Predictions, classifications, generated content

Strengths: Fast, scalable, pattern detection

Weaknesses: Feedback loops, biased training data

💳 Transaction Data

Methods: Automated recording of business transactions

Strengths: Accurate, complete records, high veracity, factual

Weaknesses: Only captures completed actions, not intent or reasons

Generation Method Impacts Data Quality

Quality Factor Human Surveys Sensor Data AI Predictions Transaction Logs
Accuracy Variable (subject to errors, bias) Very High (objective measurements) Depends on training data Very High (exact records)
Completeness Often incomplete (skipped questions) Complete (continuous capture) Complete within scope Complete (all fields required)
Timeliness Slow (manual process) Real-time Fast (near real-time) Real-time
Context Rich (explanations, reasons) None (just numbers) Limited (statistical patterns) Limited (factual only)

Implication for Software Development

Choose data generation methods based on what you're trying to achieve. User requirements gathering needs human input for context; performance monitoring needs sensor data for accuracy; personalisation needs transaction data for patterns.

Interrelationships: Source Affects Information Quality

🔗 The Chain of Influence

Data generation method → Data quality → Information quality → Decision quality. Each link in the chain affects the next.

❌ Poor Chain Example

  1. Generation: Survey with leading questions ("Don't you agree our app is great?")
  2. Data Quality: Biased responses, low validity
  3. Information: "95% of users love the app"
  4. Decision: Don't invest in improvements (incorrect)
  5. Outcome: App remains flawed, users leave

✅ Good Chain Example

  1. Generation: Neutral survey + usage analytics + support tickets
  2. Data Quality: Balanced, accurate, comprehensive
  3. Information: "60% satisfied, but checkout process has high abandonment"
  4. Decision: Prioritise checkout redesign
  5. Outcome: Improved conversion rate, happier users

⚠️ Critical Insight

You cannot fix poor-quality data with sophisticated analysis. "Garbage in, garbage out" (GIGO) means that flawed data, no matter how well analysed, produces unreliable information and poor decisions.

Context Transforms Data into Information

📝 The Same Data, Different Contexts

Raw data: "82"

Context 1: Temperature

Information: "82°C - Water is very hot, near boiling"

Action: Wait before drinking

Context 2: Test Score

Information: "82% - Student achieved a B grade"

Action: Good performance, minor improvement needed

Context 3: Heart Rate

Information: "82 BPM - Normal resting heart rate"

Action: No medical concern

Software Development Example

Data: "Response time: 250"

Without Context: Meaningless number

With Context: "API response time: 250ms - Within acceptable limits (<500ms target)"

Adding Context in Software Development

• Metadata (labels, units, timestamps) • Baseline comparisons (previous periods) • Thresholds (acceptable ranges) • Related metrics (CPU + memory together) • Business context (what action triggered this data)

Suitability for Requirements Gathering

💭 Understanding What Users Need

Requirements gathering determines what software should do. The data generation method must capture user needs, preferences, and pain points.

✅ Highly Suitable

  • User interviews: Rich qualitative insights, understand "why"
  • Focus groups: Discover needs through discussion
  • Surveys with open questions: Allow users to express desires
  • Observation studies: Watch how users interact with current systems
  • Prototype feedback: Iterate based on user reactions

❌ Unsuitable

  • Sensor data: No insight into what users want, just measurements
  • Server logs: Show what happened, not what should happen
  • AI predictions alone: Can't predict entirely new features users haven't mentioned
  • Transaction data: Shows past behaviour, not future desires

Example: Mobile Banking App Requirements

Suitable approach: Conduct user interviews discovering customers struggle to find transaction history → Requirement: "Clear, searchable transaction history on home screen"

Unsuitable approach: Analyse server logs showing page views → Can't tell you what features users wish existed

Suitability for Testing Data

🧪 Ensuring Software Works Correctly

Testing requires data that covers typical use cases, edge cases, and invalid inputs to verify the software handles all scenarios properly.

✅ Highly Suitable

  • Synthetic test data: Controlled, specific scenarios (boundary testing)
  • Production data (anonymised): Real-world scenarios and edge cases
  • Transaction logs: Actual user workflows to replay
  • Generated datasets: Large volumes for performance testing

E-commerce testing: Create orders with £0.01, £999,999.99, negative values, special characters in names—test boundary conditions

❌ Less Suitable

  • User surveys: Don't provide actual data to test with
  • Small samples: Won't reveal rare bugs or performance issues
  • Single-source data: Doesn't cover all scenarios
  • Real production data (unmodified): GDPR/privacy violations, security risks

Critical: Never use real customer PII in test environments without anonymisation!

Suitability for Analytics & Metrics

📊 Measuring Software Performance & Usage

Analytics requires accurate, continuous, quantitative data to track KPIs, performance metrics, and user behaviour patterns.

✅ Highly Suitable

  • Automated logging: Captures every event consistently
  • Sensor/IoT data: Precise performance measurements (CPU, memory, latency)
  • Transaction data: Complete records of user actions
  • Analytics tools: Google Analytics, Mixpanel (user journeys)
  • A/B testing data: Statistical comparison of variants

Example: Website analytics automatically tracks page views, bounce rates, conversion funnels—millions of data points analysed to understand user behaviour patterns

❌ Unsuitable

  • Manual surveys: Too slow, incomplete picture, biased sample
  • Anecdotal reports: Not statistically valid
  • Incomplete logs: Missing data creates blind spots
  • Inconsistent data: Different measurement methods over time

Key Metrics for Software

• Performance: Response time, throughput, error rates • Usage: Active users, feature adoption, session duration • Business: Conversion rates, revenue per user, churn rate

Suitability for User Research

🔍 Understanding User Behaviour & Motivations

User research uncovers the "why" behind user actions—motivations, frustrations, workflows, and needs. This requires qualitative and quantitative methods combined.

Combined Approach Works Best

Quantitative Data

What: Analytics show "what" users do

  • Where users click
  • Which features used most
  • Where users drop off
  • How long tasks take

Suitable sources: Analytics, heatmaps, session recordings, transaction logs

Qualitative Data

Why: Research reveals "why" users act this way

  • Motivations for behaviour
  • Pain points and frustrations
  • Workarounds they've created
  • Unmet needs

Suitable sources: Interviews, usability testing, surveys, feedback forms

Example: E-learning Platform Research

Quantitative: Analytics show 70% of students abandon courses at module 3

Qualitative: Interviews reveal module 3 is too difficult without prerequisite knowledge

Combined insight: Add prerequisites checker and introductory content before module 3

Result: Course completion rate increases to 85%

Making Judgements: Accuracy & Reliability

🎯 Accuracy

Question: Is the data correct and precise?

Assessment Criteria:

  • How was it measured/collected?
  • What's the margin of error?
  • Has it been validated?
  • Are there known issues with the source?

High accuracy: Temperature sensor calibrated to ±0.1°C

Low accuracy: User self-reported age (people lie)

🔄 Reliability

Question: Can we consistently trust this source?

Assessment Criteria:

  • Does it produce consistent results?
  • How often does it fail?
  • Can we verify the data?
  • What's the track record?

High reliability: Bank transaction logs (audited, consistent)

Low reliability: Crowdsourced data from anonymous users

Software Development Application

When choosing data for bug reports: System logs (high accuracy, high reliability) are better than user descriptions (low accuracy—"it's broken" isn't specific—but valuable for context). Combine both for best results.

Making Judgements: Relevance & Completeness

🎯 Relevance

Question: Does this data actually help answer our question?

Assessment Criteria:

  • Is it directly related to the problem?
  • Does it provide actionable insights?
  • Is it at the right level of detail?
  • Does it match the use case?

Relevant: For optimising checkout flow, track cart abandonment rates and error messages

Irrelevant: User's favourite colour won't help fix checkout bugs

📋 Completeness

Question: Do we have all the data we need?

Assessment Criteria:

  • Are there gaps in coverage?
  • Are all scenarios represented?
  • Is the time period sufficient?
  • Do we have enough samples?

Incomplete example: Testing only on Chrome desktop when 40% of users are on mobile Safari—missing critical bugs

Making Judgements: Timeliness & Cost

⏰ Timeliness

Question: Is the data current enough for our needs?

Considerations:

  • Real-time needs: Stock trading, fraud detection require immediate data
  • Recent trends: User preferences change—last month's data may be stale
  • Historical value: Long-term patterns require years of data

Suitable timeframe: For sprint planning, last 3 sprints' velocity data

Too old: Using 2-year-old velocity when team has changed significantly

💰 Cost

Question: Is obtaining this data worth the resources?

Cost Factors:

  • Collection cost: Time, tools, personnel
  • Storage cost: Database capacity, cloud storage
  • Processing cost: Computational resources, analysis time
  • Opportunity cost: Could resources be better spent elsewhere?

Trade-off: Detailed user surveys provide rich insights but take weeks and cost thousands. Simple analytics are instant and free but less detailed.

Trade-offs in Data Selection

⚖️ Balancing Competing Priorities

Perfect data rarely exists. Software developers must balance accuracy, speed, cost, and completeness based on project needs.

Scenario Priority Trade-off Accepted Rationale
MVP Launch Speed to market Limited user research, basic analytics Quick validation more important than perfect data—iterate later
Banking Software Accuracy & reliability Higher cost, slower collection Financial accuracy is non-negotiable—worth the investment
Performance Optimisation Precision & completeness Complex instrumentation, detailed logs Need exact measurements to identify bottlenecks
User Research Study Depth of insight Small sample size, high time investment Rich qualitative data from 10 users beats shallow data from 1,000
A/B Testing Statistical significance Wait for enough data before deciding Premature conclusions from small samples lead to wrong decisions

Real-World Scenario: Mobile App Development

📱 Fitness Tracking App

Challenge: Determine which new feature to develop next

Data Available

  • Analytics: Current feature usage rates (high accuracy, large sample)
  • App store reviews: User complaints and requests (biased sample—angry users more vocal)
  • User survey: 200 responses about desired features (voluntary response bias)
  • Competitor analysis: Features in rival apps (secondary source)
  • Support tickets: Issues users report (problem-focused, not aspirational)

Judgement Process

  1. Most relevant: User survey (directly asks what they want) + analytics (shows what they actually use)
  2. Support findings: Survey shows 60% want meal planning integration
  3. Validation: Analytics confirm nutrition tracking is heavily used feature
  4. Competitor check: Top rival lacks this feature—opportunity!
  5. Decision: Prioritise meal planning feature

Why This Works

Combined multiple data sources (triangulation) to offset individual weaknesses. Survey showed demand, analytics confirmed related feature usage, competitor analysis validated uniqueness. No single source was perfect, but together they provided strong evidence.

Real-World Scenario: Website Performance

🌐 E-commerce Site Slowdown

Problem: Customers complaining about slow page loads, but cause unknown

Available Data Sources

  1. Customer complaints: "Site is slow" (subjective, lacks detail)
  2. Server logs: Response times, error rates (objective, precise)
  3. Monitoring tools: CPU, memory, network usage (real-time, accurate)
  4. User analytics: Actual page load times by browser/location

Suitability Analysis

✅ Most Suitable

Server logs + monitoring tools

Objective, precise measurements identify exact bottleneck—database queries taking 3+ seconds

❌ Less Suitable

Customer complaints alone

Useful to identify issue exists, but too vague to pinpoint solution

Resolution Process

Step 1: Monitoring tools show database CPU at 95% during peak hours

Step 2: Server logs identify slow queries accessing unindexed tables

Step 3: Add database indexes to frequently queried columns

Result: Page load times drop from 4 seconds to 800ms—problem solved

Validation: User analytics confirm improvement, complaints cease

Critical Evaluation Framework

🔍 Systematic Approach to Judging Data Suitability

Use this framework when evaluating whether data is suitable for your software development needs.

The 7-Question Framework

  1. Purpose Alignment: Does this data directly address our specific question or need?
  2. Generation Method: How was this data collected, and does the method affect reliability?
  3. Quality Assessment: Is it accurate, complete, consistent, and current?
  4. Sample Adequacy: Is the sample size sufficient and representative?
  5. Context Availability: Do we have enough context to interpret this data correctly?
  6. Trade-off Justification: Are any limitations acceptable given our constraints (time, budget, accuracy needs)?
  7. Alternative Consideration: Is there better data available, or should we combine multiple sources?

Document Your Reasoning

In professional software development, document why you chose specific data sources and what limitations you accepted. This justifies decisions to stakeholders and helps future teams understand your reasoning.

Exam-Style Questions

Question 1 (6 marks)

Scenario: A software development team is building a new feature for their mobile app. They have two data sources to help them decide how to design the user interface:

  • Source A: Analytics data showing 80% of users access the app on smartphones with screens smaller than 6 inches
  • Source B: A user survey (20 responses) where 15 users said they prefer large buttons and simple interfaces

Question: Evaluate the suitability of each data source for making UI design decisions. Which source is more suitable and why?

19 / 23

Question 1: Model Answer

Source A Evaluation (3 marks)

The analytics data showing 80% of users have screens smaller than 6 inches is highly suitable for UI design decisions ✓. This data is objective, based on actual device measurements from the app's entire user base, providing high accuracy and reliability. It directly informs design choices—small screens require larger touch targets, simplified layouts, and thumb-friendly navigation ✓. The large sample size (all app users) makes it statistically significant and representative, unlike a small survey. This quantitative data provides concrete constraints for the design—the team knows definitively that they must optimise for small screens ✓.

Source B Evaluation (2 marks)

The user survey with 20 responses provides useful qualitative insight into user preferences ✓, but has significant limitations. The sample size is too small to be statistically significant—20 responses may not represent the entire user base accurately. There's potential for response bias (people who respond to surveys may have different preferences than those who don't). However, the finding that 75% prefer large buttons and simple interfaces does validate the direction suggested by Source A ✓.

Conclusion (1 mark)

Source A (analytics) is more suitable as the primary data source for UI decisions because it provides objective, comprehensive data about actual usage constraints ✓. However, the ideal approach would combine both sources—use Source A to define technical requirements (button sizes must work on small screens) and Source B to validate that users appreciate simplified interfaces. The survey confirms users want what the analytics data suggests they need.

Exam-Style Questions

Question 2 (8 marks)

Scenario: A development team is investigating why their web application crashes intermittently. They are considering three data sources:

  • Source 1: User-reported bug descriptions via email ("The app crashed when I clicked the button")
  • Source 2: Automated server error logs with timestamps, error codes, and stack traces
  • Source 3: User surveys asking about crash frequency and circumstances

Question: Analyse the interrelationships between these data sources and evaluate their suitability for debugging the application. Explain which combination of sources would be most effective and why.

21 / 23

Question 2: Model Answer

Interrelationships (3 marks): These three data sources are interconnected and complementary ✓. User-reported bugs (Source 1) provide context about what users were trying to accomplish when crashes occurred, but lack technical precision about the underlying cause. Server error logs (Source 2) provide exact technical details (error codes, stack traces) that pinpoint the code causing crashes, but don't explain the user's perspective or steps to reproduce ✓. User surveys (Source 3) could identify patterns in crash frequency and common scenarios, but rely on user memory which may be unreliable and lack technical detail. Each source compensates for weaknesses in the others—combining them creates a complete picture ✓.

Suitability Analysis (3 marks): Source 2 (server logs) is most suitable for actually debugging the application ✓ because error logs provide objective, precise technical information necessary to identify and fix code errors. The stack traces show exactly which line of code failed and under what conditions. This data is highly accurate, complete, and generated automatically in real-time. However, Source 1 (user reports) is valuable for reproduction steps ✓—knowing "the crash happens when clicking the submit button on the checkout page" helps developers reproduce the bug reliably. Source 3 (surveys) is least suitable for debugging ✓ because it's too slow, relies on subjective user memory, and doesn't provide technical detail, though it might help prioritise which crashes to fix first based on frequency.

Recommendation (2 marks): The most effective approach combines Sources 1 and 2 ✓. Start with server error logs to identify when and where crashes occur technically, then correlate these with user bug reports to understand the user actions triggering the errors. For example, error logs might show "NullPointerException at line 247" whilst user reports explain "crashed when checkout form was empty"—together revealing that the code doesn't handle empty form submission. This combination provides both technical precision for fixing the bug and user context for testing the solution ✓. Source 3 is less critical for debugging but could be used afterwards to verify the fix resolved user-facing issues.

Summary: Data & Information Interrelationships

Key Takeaways

  • Hierarchy: Data becomes information when given context; information becomes knowledge when applied with understanding
  • Generation Method Matters: How data is created (human, sensor, AI, transaction) fundamentally affects its quality, accuracy, and suitability
  • Interrelationships: Data source → data quality → information quality → decision quality. Flawed data produces flawed decisions ("garbage in, garbage out")
  • Context is Essential: The same raw data means different things in different contexts—labels, units, baselines, and business context transform data into actionable information
  • Suitability Varies by Purpose: Human input suits requirements gathering; sensors suit performance monitoring; transaction data suits analytics; combine sources for research
  • Judgement Criteria: Evaluate data on accuracy, reliability, relevance, completeness, timeliness, and cost—perfect data rarely exists
  • Trade-offs Required: Balance speed vs accuracy, cost vs completeness, depth vs breadth based on project priorities and constraints
  • Software Development Application: Different development phases need different data—requirements need qualitative insight, testing needs controlled scenarios, analytics needs quantitative measurements

🎯 Remember

Critical thinking about data suitability is essential for successful software development. Don't accept data at face value—question its origin, assess its quality, understand its limitations, and choose sources that genuinely serve your needs. When possible, combine multiple data sources to offset individual weaknesses and strengthen conclusions.
